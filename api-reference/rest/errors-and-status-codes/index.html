Errors and Status Codes

📕 REFERENCE · Audience: API Consumer · Use: look up what a fixed reader REST response carries and which status codes the specification actually declares

Everything on this page is read out of the vendor's OpenAPI 3.1 document (IoT Connector REST API (FXR60 / FXR90), version 3.0.0) — the same document the operation reference is generated from. Nothing here is inferred from HTTP convention. Where the document is silent, this page says so rather than filling the gap.

Fixed readers only

These codes belong to the FXR60 / FXR90 REST surface. The RFD40 / RFD90 handheld sleds speak MQTT, and their application-level codes are a different, much larger set — see Response Codes in the MQTT reference.

The Declared Status Codes​

Across all 73 operations the document declares four distinct HTTP status codes, and no others.

StatusDeclared byDescription in the documentBody
200all 73 operationsOK (72) · Success (1, the login call)Varies — see What a 200 Carries
4001 operationErrorcode + message
4221 operationUnprocessable Entitymessage only
5003 operationsError (1) · Internal Server Error (2)code + message

Two things follow from that table and are worth stating plainly:

  • 200 is the entire documented success surface. No operation declares 201, 202, 204 or any other 2xx.
  • There is no catch-all. The document declares no default response, no ranged responses (4XX, 5XX), and no reusable components.responses block. A status code not listed above is not defined-and-omitted — it is simply outside the document.

Every declared body, success or error, is application/json. No operation declares any other media type.

What a 200 Carries​

A 200 does not imply a payload. The 73 success responses fall into four shapes:

ShapeOperationsWhat you get
JSON object33A populated object — for example the reader identity from GET /cloud/version
Empty string30Schema is type: string, described as "Returns an empty string on success." The shape used by operations that only apply or clear a setting, such as PUT /cloud/app-led
JSON array4A list
No body declared6The 200 carries a description and no content at all: PUT /cloud/start, PUT /cloud/stop, PUT /cloud/certificates, PUT /cloud/bleConfig, DELETE /cloud/logs/syslog and DELETE /cloud/logs/radioPacketLog

The One Application-Level Code in a Success Body​

Exactly one operation returns a status field inside a 200. GET /cloud/localRestLogin answers with a two-field object, and the document's own example shows code as 0 on success with the bearer token in message:

{
"code": 0,
"message": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}

No other operation's success body carries a code field, so there is no site-wide application-level code scheme on this API. Read the HTTP status, not a body field — the login call is the single exception. This is the sharpest difference from the handheld MQTT surface, where every reply carries a response.code.

Placeholder — not declared by the specification

Not yet documented. The document gives no meaning for any code value other than the 0 in that login example, and enumerates no failure values for it. What a non-zero code from the login call signifies is not stated.

The Three Operations That Declare an Error​

Error responses exist for three operations out of 73. They are listed here in full because the list is the whole documented error surface.

OperationCodesBody of each
PUT /cloud/cableLossCompensation400, 500code + message
GET /cloud/impinjGen2X500code + message
PUT /cloud/impinjGen2X422, 500422 → message only · 500 → code + message

For the other 70 operations the document declares no error response at all. That is a gap in the document, not a guarantee that those operations never fail.

The Two Error Body Shapes​

Four of the five error responses use the same object, and the 422 uses a reduced form of it.

code + message — used by every 400 and every 500:

{
"code": 0,
"message": "string"
}

code is typed number and message is typed string. Neither is marked required, and the document supplies no example for any error body, so the values above are placeholders showing the types, not a real response.

message alone — used by the single 422, on PUT /cloud/impinjGen2X:

{
"message": "string"
}

Each of the five error responses points at its own schema (SetCablelosscompensationResponse400, SetCablelosscompensationResponse500, GetImpinjGen2XResponse500, SetImpinjGen2XResponse422, SetImpinjGen2XResponse500) rather than at one shared error model. The shapes coincide; the document does not oblige them to.

What the Document Does Not Declare​

Placeholder — not declared by the specification

Not yet documented. No authentication or authorization failure is described anywhere in the document. It declares two security schemes — basicAuth on the login call, bearerAuth on the other 72 operations — and then declares no 401 and no 403 against any of them. What a reader returns for a missing, malformed or rejected credential is not specified here; treat it as undocumented rather than as "never happens".

Placeholder — not declared by the specification

Not yet documented. No numeric code value carried in a 400, 422 or 500 body is enumerated or explained. The field is typed number and nothing more, so the codes cannot be branched on from this document alone.

Placeholder — not declared by the specification

Not yet documented. Nothing states how a reader responds to a path that does not exist, a method that is not allowed on a valid path, or a malformed JSON body — the document declares no 404, 405 or parse-failure response for any operation.

The transport these responses arrive over is undeclared too: the document has no servers block, so it fixes neither URL scheme nor port. See Your First REST Call for what that means when you make the call.
