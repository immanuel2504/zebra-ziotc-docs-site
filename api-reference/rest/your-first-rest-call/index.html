Your First REST Call

📙 HOW-TO · Audience: API Consumer · Time: ~10 min

This page is orientation for the FXR60 / FXR90 fixed reader REST API — what you need before the first call, how to authenticate, what a response looks like, and how to find the operation you want. It is not a product tutorial: for installation and product-level guidance on the fixed reader line, use Zebra's fixed reader product documentation.

Everything below is taken from the vendor's OpenAPI 3.1 document (IoT Connector REST API (FXR60 / FXR90), version 3.0.0), which is the same document the operation reference renders.

Fixed readers only

The RFD40 / RFD90 handheld sleds do not expose this API. Their IoT Connector interface is MQTT — see the MQTT API.

What You Need​

RequirementDetail
A reachable readerThe document declares no servers block, so it carries no host. Take the address from the reader's own network configuration.
Admin credentialsThe login operation is authenticated with HTTP Basic using the reader's Admin login credentials.
An HTTP clientAnything that can set an Authorization header. The examples here use curl.

The Base URL​

The document specifies the path of each operation and nothing in front of it. Every path begins with /cloud/ — /cloud/version, /cloud/mode, /cloud/certificates/{certname} — and a request is that path appended to the reader's own address.

Placeholder — not declared by the specification

Because there is no servers block, the document fixes neither the URL scheme (http or https) nor the port the reader listens on. Both have to come from the reader's network configuration or from Zebra's fixed reader product documentation.

The operation reference therefore shows https://reader.invalid in front of every path, in the operation header and in the copyable request samples. That host is a placeholder standing in for your reader, serving the same purpose as <admin-user> and <reader-base-url> below: .invalid is a reserved name that can never resolve (RFC 6761), so a sample pasted unchanged fails immediately instead of reaching the wrong machine. Substitute your reader's own address.

The same gap is why the operation reference has no Send button: an interactive console with no host cannot reach anything.

Make the First Call​

1. Obtain a Bearer Token​

GET /cloud/localRestLogin is the only operation in the document secured with HTTP Basic; the other 72 are secured with a bearer token. It takes no request body.

Shell
curl -u '<admin-user>:<admin-password>' \
  '<reader-base-url>/cloud/localRestLogin'

The response carries the token in message, and code is 0 on success:

{
"code": 0,
"message": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}

If a token has already been copied from the reader's dashboard page, use that instead — the login call exists to mint one, not to be a mandatory first step.

2. Call an Operation with the Token​

Every other operation expects the token in an Authorization header. GET /cloud/version is a good first read: no body, no parameters, and the response identifies the reader.

Shell
curl -H 'Authorization: Bearer <token>' \
  '<reader-base-url>/cloud/version'

The document's example response:

{
"availableOsUpgrades": {},
"cloudAgentApplication": "0.6.2.64",
"model": "FXR60",
"radioControlApplication": "0.2.58.7",
"radioFirmware": "2.1.70.0",
"readerApplication": "5.0.3",
"revertBackFirmware": {},
"serialNumber": "260995251E0047"
}

3. Send a Body When the Operation Takes One​

31 of the 73 operations declare a request body, and every one of them is application/json. PUT /cloud/app-led is the smallest example:

Shell
curl -X PUT \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"color":"amber","flash":true,"seconds":60}' \
  '<reader-base-url>/cloud/app-led'

What Responses Look Like​

  • Every one of the 73 operations declares a 200. That is the whole documented success surface.
  • A 200 is often an empty body. 30 of the response schemas are documented as "Returns an empty string on success" — the shape used by operations that only apply or clear a setting. PUT /cloud/app-led above is one of them.
  • Errors are documented for three operations only. PUT /cloud/cableLossCompensation declares 400 and 500; GET /cloud/impinjGen2X declares 500; PUT /cloud/impinjGen2X declares 422 and 500. Those bodies carry code (number) and message (string), except the 422, which carries message alone.
  • For the other 70 operations the document declares no error response at all, so a non-200 from them is undocumented here rather than defined and omitted.

How the Reference Is Organized​

The operation reference is grouped by the document's own tags, so the grouping is the one the API's authors chose — 73 operations across 15 categories: Login, Control, System, Network, Certificate, Logs and the rest. By method it is 35 GET, 34 PUT and 4 DELETE. The categories are the collapsible groups in the reference's own sidebar; they have no page of their own.

Each operation shows the method and path, any path parameters, the request schema and the response schemas, alongside a request sample you can copy in your language of choice.

Schemas render inline

The document's 134 component schemas are not published as pages of their own. Each one is rendered inline on every operation page that uses it, under the request and response sections — so the place to read a schema is the operation you are calling, not a separate model index.
